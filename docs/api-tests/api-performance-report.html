SortPi API test report: why the app and the website feel slow

5 November 2026Live shop sirajdawakhana.sortpi.comLocal demo shopTested from a Mac in Bangladesh

Short answer

The SortPi code is fast. The same 146 read calls take a median of 9 ms on a local copy. On the live shop the median is 311 ms. The slowness comes from where the server sits and how it handles a burst of calls, and only partly from the apps.

  1. Distance. The live server is in France (Contabo), about 200 ms from Bangladesh, with no CDN in front. Every call pays that, and a new connection costs about 0.8 to 1.0 s before any data arrives.
  2. The server queues bursts. One call takes 292 ms. Sixteen at the same moment take up to 1.4 s. The website dashboard sends 15 calls at once and the phone's Home screen sends about 7, so each one waits in line.
  3. Random slow first calls. Some endpoints take seconds the first time and a fraction of that on repeat: /inventory/stock/ took 5.0 s then 0.24 s. This happened on a shop with almost no data.
  4. The phone app added a wait of its own after the fingerprint prompt. That part is fixed in code and still needs a check on the Pixel.

1. Where one call's time goes

A typical live call takes about 311 ms. Only a few milliseconds of that are SortPi's own code.

network round trip 200 ms
TLS, proxy, slower server about 100 ms
SortPi code about 9 ms (measured locally)distance to France 200 ms (ping)remainder, estimated

A new connection is slower still. From the Mac: 0.2 s to connect, 0.25 to 0.45 s more for TLS, then the call itself. A reused connection answers in 0.23 s.

2. The server queues bursts of calls

I sent N identical tiny read calls at the same instant and timed the slowest. A single call takes 292 ms. Past about four at once, calls start waiting for each other.

3. The website: the page is quick, the data is not

The dashboard page itself loads fast. The wait is for its data, which arrives in one crowded burst.

Two calls are made twice: /auth/me and /dashboard/. The two stock calls ask for up to 200 rows each. Fonts and scripts are not the problem; scripts were already cached on the repeat visit.

4. The phone app

Opening the app does the same in order: connect (about 1 s), ask /auth/me (0.34 to 0.69 s), then Home starts about 7 calls in one burst. On the Mac's wifi that adds up to 2.5 to 3.5 s. Mobile data makes every round trip longer, which fits the 5.08 s p90 in Firebase.

One more wait was the app's own doing. It asked /auth/me only after the fingerprint passed, so you looked at a lock screen with a live Unlock button, and touched again. The call now starts while the prompt is open, the button shows "Opening your shop…", and it ignores extra taps. This is in the code, tested in unit tests, and not yet tried on the real Pixel.

7. Findings

#LevelFindingSuggested fix
1HighThe server handles about 4 requests at once. 16 at once take up to 1.4 s each.Raise gunicorn workers or threads to match the CPU cores. Measure again with the burst test.
2HighServer in France, no CDN. 200 ms per call, about 1 s per new connection.Move the server near Dhaka (for example Singapore), or put Cloudflare in front with one proxied record per shop (a wildcard cannot be proxied on a normal plan).
3HighSlow first calls: live /inventory/stock/ 5.0 s, /sales/summary/ 2.0 s, /users/ 1.7 s. Local /customers/ 8 s after cache expiry.Warm or refresh the caches on write, lengthen the TTL, and add the customer totals without a join over all sales.
4MediumThe website dashboard sends 15 calls at once, and calls /auth/me and /dashboard/ twice.Remove the duplicates. Later, one start-up call that returns what Home needs.
5Fixed in codePhone: waited for /auth/me only after the fingerprint, with a live Unlock button.Done. Retest on the Pixel after the next staging build.
6MediumDeleting a customer or supplier is a soft delete. It stays in the lists as inactive. The phone's customer list does not filter inactive ones.Decide whether lists hide inactive records by default. Check the phone's list.
7LowHEAD on a list runs the whole query (8 s on a cold local cache). limit=100000 is accepted.Answer HEAD without the query. Set a maximum page size.
8LowOPTIONS and DELETE on a list return 403 PERMISSION_DENIED, not 204 and 405.Return the standard answers.
9LowListed in the API spec but 404 on the live shop: /customers/refills/, /inventory/modal/, /inventory/serials/.Confirm they are switched off by shop type, or remove them from the spec.
10LowA replayed sale (same key) takes 987 ms live, against 39 ms locally. It is correct, only slow.Follows from findings 1 to 3.

8. What the live test left behind

Every record was named ZZ-API-TEST and removed. All clean-up deletes returned 204. The test did change the live shop in these ways:

  • One test sale (a 1.00 item, paid in cash) and its full cash return. They show in the sales list and in today's sales and return totals, and cancel each other out.
  • Two inactive records that the API cannot delete: customer ZZ-API-TEST L3CPU customer and supplier ZZ-API-TEST L3CPU supplier, both with a balance of 0.
  • Stock counts on the test item only. The item, its category and its unit were deleted.

I left out anything that messages people or changes the business itself: billing, users and roles, shop reset, closing the shift or the day.

9. What to do first

  1. Server workers (finding 1). Cheap, and it speeds up every burst on the website and the phone. Needs access to the server.
  2. Cache the last sign-in on the phone. Mobile only. Home opens at once from the last known permissions and refreshes in the background.
  3. Warm the slow endpoints (finding 3) and remove the website's duplicate calls (finding 4).
  4. Distance (finding 2). The biggest single gain, and the biggest job. Decide between a nearer server and Cloudflare with one record per shop.

10. How this was measured, and what it cannot tell you

  • All timings come from a Mac on wifi in Bangladesh, using the browser's own timers. They are not from the phone on mobile data. The phone figure is Firebase's 5.08 s p90, and the chain in section 4 is my reading of it.
  • The live shop has almost no data (most lists are empty). Heavier shops will be slower on the report endpoints.
  • The worker count and CPU load of the server were not inspected. Finding 1 is inferred from the burst test.
  • The live run used the same requests as the Postman collection, sent from the signed-in browser page. Newman ran the collection itself on the local copy.
  • To run it yourself: import SortPi-API-full-test.postman_collection.json and an environment file from mobile/SortPi/docs/api-tests/ into your own Postman workspace, fill in email and password, and run the folders in order. Use newman run for the command line.
